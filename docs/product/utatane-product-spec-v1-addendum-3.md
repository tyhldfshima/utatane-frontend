## 33. #1 許諾とポリシーを分ける／公開時の再検証

### 33-1. 確定の文

> #1 修正して承認：公開時再検証は採用。ただし「条件変更後は必ず不許可」ではなく、その派生について既に成立した許諾が公開前の条件変更で失効するのかを許諾ルールとして明示する。初期商品ルールは「公開時点で有効な許諾必須」でよい

### 33-2. 仕様としての持ち方＝3つを別々の物として持つ

| | ① 貢献の現在の再利用ポリシー | ② 個別に成立した Permission/Consent | ③ 公開時の再検証の結果 |
|---|---|---|---|
| 何か | 貢献ごとの「これからの利用」への一般的な設定（自由／申請して承認／使えない ＋ どこで）。追補1 19章の器 | 特定の相手・特定の派生に対して成立した許諾という「出来事」 | ある Version を公開しようとした時点で、参照した貢献ごとに許諾が有効だったかを確かめた結果 |
| 持つ項目 | 貢献／ポリシーの値／版番号／いつから／誰が設定したか | 誰が（許諾した権利者。共作なら全員、または委任を受けた代表者と委任の記録）／誰へ（利用する人）／どの派生について（下書きの Version、または募集）／どの貢献を／いつ成立したか／根拠（申請への承認・募集の事前承認（34章）・ポリシーが「自由」だったことによる成立・委任に基づく代表者の承認）／成立時のポリシーの版／成立時の許諾ルールの版／状態（有効・取り消し・失効）とその履歴 | 公開しようとした Version／日時／参照した貢献ごとに：その時点のポリシーの版・使った Permission・適用した許諾ルールの版・結果（通過／不通過）・不通過の理由 |
| 変わり方 | 版を重ねる（上書きしない） | 成立の記録は消さない。取り消し・失効も新しい記録として足す | 公開の試みごとに1件。消さない |
| 誰が見られるか | 誰でも（その貢献を使おうとする人） | 許諾した人と、許諾を受けた人 | その Version の参加者と、使われた貢献の権利者 |

★「承認」という出来事（②）と「現在の再利用設定」（①）は別物。①を変えても、②の記録は書き換わらない。②が有効か失効したかは、次の許諾ルールで決まる。

### 33-3. 許諾ルール（明示する項目）

許諾ルールは、全体に1つの版つきの決まりとして持つ（将来、貢献ごと・募集ごとに持たせる余地は残す）。

| 項目 | 取りうる値 | 初期の商品ルール |
|---|---|---|
| R1 公開に必要なこと | 公開時点で、参照した各貢献について有効な許諾（ポリシーが「自由」であるか、有効な Permission があること）が必要 | ★「公開時点で有効な許諾が必須」（確定） |
| R2 公開前にポリシーが変わったとき、既に成立した Permission が失効するか | (a) 失効しない（成立済みの許諾は、許諾した人が個別に取り消さない限り有効） (b) 失効する (c) ポリシーを変えるときに、許諾した人が「個別の許諾も取り消すか」を選ぶ | ★この項目を明示することが確定。値は③で法的な権利との関係を整理して決める（38章 要判断 AD-1）。推し＝(c)：ポリシーを変える画面で、成立済みで未公開の Permission の一覧を出し、「残す／取り消す」を許諾した人に選ばせる。どちらを選んだかを②の新しい記録に残す。自動ではどちらにも倒さない |
| R3 公開後の取り消し | 公開済みの派生に対する許諾を後から取り消せるか | 本編15-15（31-9）。③へ（40章） |
| R4 許諾の届く範囲 | 許諾は「その派生1つ」に対して成立する（追補1 21-1 の4） | 変わらず |

- 再検証（③）は R1 と R2 に沿って行う。不通過なら公開しない。利用する人には、ポリシーが変わった時点で通知が届く（確定7）。
- 安全側の運用：R2 の値が決まるまでは、R2 に当たる場面（成立済み・未公開の Permission があるのにポリシーが厳しくなる）で、上の (c) の画面で許諾した人の選択を必ず記録し、選択が無い Permission は公開時に「有効かどうか要確認」として不通過にする。

## 34. #2 募集の事前承認

### 34-1. 確定の文

> #2 承認：募集時に「この募集から成立する利用は事前承認済み」を設定可能にする

### 34-2. 仕様としての持ち方

- 募集（本編10章）に、作者が「この募集から成立する利用は事前承認済み」を設定できる。既定は設定しない（確定4の初期値「申請→承認」のまま）。
- 設定の中身：どの貢献の／どの役割での利用か／募集の期間・人数。共作の貢献なら、設定そのものに35章の承認方式（全員承認か、委任を受けた代表者）が要る。
- 応募して参加が成立した時点で、②の Permission/Consent を1件記録する：根拠＝募集の事前承認／募集の番号／誰が（募集を出した権利者）／誰へ（応募した人）／どの派生について（応募でできた下書き）／成立時のポリシーの版。
- 公開時の再検証（33章）はこの Permission にも同じように行う。
- 募集を閉じた後の新しい利用は、事前承認の対象にならない（通常の申請に戻る）。
- ケース65（M1：MVP の体験が止まる）はこれで解ける（38章）。

## 35. #3 共作の承認方式／アカウント状態と権利状態の分離

### 35-1. 確定の文

> #3 修正して承認：共作時に承認方式を決める。ただし「どちらか1人の承認」を無条件には許さず、全員承認／代表者へ承認権限を委任を基本にする

### 35-2. 承認方式

| 方式 | 中身 | 記録 |
|---|---|---|
| 全員承認 | 共作の貢献の再利用には、権利者全員の承認が要る | 申請ごとに、権利者1人ずつの返事を②に残す |
| 代表者へ委任 | 権利者全員が、あらかじめ特定の代表者へ「再利用の承認権限」を委任する。代表者の承認で成立 | 委任そのものを、権利者1人ずつの同意の記録（委任した人・委任を受けた人・範囲・いつから）として残す。代表者の承認は「委任に基づく」と②に書く |

- ★「どちらか1人の承認でよい」は選択肢から外す（追補2 ケース62 の例に取り消し線）。
- 承認方式は共作が生まれた時点（公開前）に決める。決めていない共作は「全員承認」として扱う（確定5の基本）。
- 委任の範囲：初期は「再利用の申請への返事」だけ。★代表者自身が利用する人になる申請は、委任の範囲の外とし全員承認にする（代表者が自分に許可を出せる形を持たない。38章の注意 A3）。
- 委任の取り消し：委任した人はいつでも取り消せる。取り消しは新しい記録で、以後の申請にだけ効く。取り消し前に代表者が出した承認（②）の扱いは 33-3 の許諾ルールに沿う。

### 35-3. アカウント状態と権利状態を別の物として持つ

| | アカウント状態 | 権利状態 |
|---|---|---|
| 何か | UTATANE のアカウントの状態：有効／退会／利用停止／連絡不能（届出・一定期間の不応答）／死亡の届出 | 貢献に対する権利者・持ち分・委任・承継の状態 |
| 退会・死亡で | 変わる | ★変わらない。権利は消えない。表示が「退会したユーザー」になっても、権利者の記録はそのまま |
| 変わるきっかけ | 本人の手続き・運営の手続き | ③で決める手続き（相続・承継・譲渡など） |

- 退会・死亡・連絡不能の権利者がいる共作は、その人の承認が必要な場面で止まる（使えない）。★残りの権利者や運営が、後から1人の判断で解く形は持たない。解き方（相続・承継）は③。
- 代表者が退会・死亡・連絡不能になった場合：委任は自動では他の人へ移らない。以後の申請は止まる（全員承認でも同じ理由で止まる）。
- 既に成立した Permission（②）は、許諾した人のアカウント状態が変わっても、それだけでは失効しない（アカウント状態は権利状態ではないため）。失効するかは 33-3 の許諾ルールと③。
- 受け取るはずの報酬の扱い（保留・承継）は③（40章）。

### 35-4. 直した箇所

- 追補2 29-3 ケース62 → 「どちらかの承認でよい」に取り消し線、方式とアカウント状態／権利状態の分離を追記
- 追補1 19-3 → 追補3 への案内を追記

## 36. #4 持ち込み素材の出どころ申告

### 36-1. 確定の文

> #4 承認：外部から持ち込む素材は出どころ申告必須。自作・共同制作・許諾済み等の根拠も記録可能にする

### 36-2. 仕様としての持ち方

- 素材（追補2 27章）を持ち込むとき、出どころの申告は必須。申告がない素材は Version に入れられない。
- 申告の種類（増やせる一覧。固定しない）：

| 申告 | 記録できる根拠 |
|---|---|
| 自作 | 作った日・制作の説明（任意で制作途中のファイル） |
| 共同制作 | 一緒に作った人（UTATANE の人なら指名し、その人の同意を記録。外部の人なら氏名・連絡先の記録） |
| 許諾済み | 許諾した人・許諾の範囲・許諾の書面や画面の写し（ファイル）・日付 |
| UTATANE 内の素材から作った | 元の素材の指定 → 元の素材が収める全ての貢献の条件（追補2 27章）がそろう必要がある |
| 外部の素材（配布されている素材など） | 出典・利用条件の名前・URL |
| AI 生成を含む | 使った道具の名前・範囲（本編ケース39） |

- 申告と根拠は、消さない記録にする（誰が・いつ・何を申告したか）。後から申告を直すときも新しい版で足す。
- 申告は運用上の記録であって、法的な権利処理の完了を意味しない（追補1 17章と同じ）。

### 36-3. ケース64（歌声の抜き出し）がどう止まるか

- Z が Version X の混ざった音源から歌声を抜き出して持ち込む。
- 正しく申告した場合：「UTATANE 内の素材から作った」＝元の素材（Version X の音源）を指定 → その音源が収める全ての貢献（曲S・編曲T・歌唱U・録音…）の条件が要る → 歌唱U の許諾が無ければ Version に入れられない（止まる）。
- 偽って「自作」と申告した場合：申告の記録が残る。権利者や聴いた人の申し立て（本編ケース41）で一時停止し、申告の記録を根拠に確かめる。偽りと分かれば、その素材と、それを参照する Version を止める。
- 照合（音の一致を機械で確かめる）は将来。第1実装は申告の記録と申し立てで止める。

## 37. #5 公開状態と Revenue Rule の変更は履歴つき新版

### 37-1. 確定の文

> #5 承認：公開状態変更・Revenue Rule変更は過去データを上書きせず履歴付き新版として扱う

### 37-2. 仕様としての持ち方

- 公開状態（公開／非公開／匿名化表示／一時停止など）は、Version ごとに版の列として持つ。変更ごとに新しい版を足す：誰が・いつ・どの状態へ・理由（本人の希望・参加者全員の合意・申し立て・法的な求め）・いつから。
- Revenue Rule の変更も新しい版（本編7章：適用開始日つき）。古い版を上書きしない。過去の収益は、その時点で有効だった版で計算したまま。
- どちらも、Version の中身（貢献の参照）を書き換えない。確定3（公開済み Version に下流の貢献を足さない）と両立する。
- 追補2 31-1 の読み（書き換えに当たらない）は、「書き換えではなく、履歴つきの新版」として確定。

## 40. ③への申し送り（追補2 32章の更新）

追補2 32章の項目に、次を足す。

### 40-1. 許諾（Permission/Consent）

- ①ポリシー・②個別の許諾・③公開時の再検証を分けた構造（33章）と、実際の法的な許諾との関係
- 許諾ルール R2（公開前のポリシー変更で個別の許諾が失効するか）の値（AD-1）
- 許諾ルール R3＝公開時の派生許可を後から取り消せるか（本編15-15／追補2 31-9）
- 募集の事前承認（34章）が法的にどこまでの許諾にあたるか
- 出どころ申告と根拠の記録（36章）が権利の確認にどこまで使えるか

### 40-2. アカウント状態と権利状態の分離

- 退会・死亡でも権利は消えない（35-3）。権利状態を変える手続き（相続・承継・譲渡）
- 連絡不能の扱い（AD-2）
- 共作で権利者が不在のときに止まったものを、どういう手続きなら解けるか（後から1人の判断で解かない、は確定）
- 代表者への委任が、代表者の退会・死亡でどうなるか

### 40-3. 資金の流れ

- 退会・死亡・連絡不能の権利者に届くはずの報酬の保留・承継と期限
- アカウントが無い権利者（承継した人など）へ届ける方法
