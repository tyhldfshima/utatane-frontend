## 26. えふさん確定1〜7（2026-09-18・原文のまま）と反映

> 1 承認＋拡張 「曲」はメロディ等の創作物と、それを利用するための素材を区別して持てる。歌唱・演奏も必要に応じて独立音源を持てる
> 2 修正 「1代前まで」で固定しない。参照・改変したContributionの由来を全世代追跡可能にし、どこまで収益対象にするかはRevenue Ruleで決める
> 3 承認 公開済みVersionを過去方向へ書き換えて下流Contributionを追加しない。変更したければ新Versionを作る
> 4 承認 初期値は「申請→承認」。作者が自由利用/不可へ変更可能
> 5 修正して承認 共作Contributionは「厳しい方を自動採用」ではなく、全権利者の必要な同意が揃わなければ利用不可を基本にする
> 6 承認＋一般化 「歌声が使われた作品」だけ専用化せず、自分のContributionが使われた作品として歌唱・演奏・詞・曲・編曲すべて表現可能にする
> 7 承認 最終判定は公開時。途中で条件変更されたら通知し、公開条件を再検証する
> 例えば、Aの曲 → Bが編曲 → Cが再編曲 → Dがさらに派生 となったとき、「1代前まで」とDB構造そのものに入れてしまうと、Aとの系譜が切れます。 内部では、由来は最後まで追える。報酬を誰まで届けるかは、そのVersionに適用されたRevenue Ruleが決める。にします。 ③の「同じ貢献は1回だけ」も少し修正します。同じContributionを同一Version内で重複参照してもContribution自体は一意に扱うのは正しいですが、「だから報酬も必ず1回」とまでは固定しません。Revenue Ruleの計算基礎と系譜の重複排除は分けます。 ここで**「作品を構成する最小単位」一覧を1枚に確定**してください。 少なくとも、詞 / メロディ・作曲 / 編曲 / 歌唱 / 楽器演奏 / 音源・録音 / MIX等 について、 何をContributionとして独立管理するのか／素材ファイルを持つのか／再利用可能か／Versionとの関係／複数人共作可能か を整理します。 ただし役割の種類を固定enumにして将来追加不能にはしない。Bで概念を確定し、④で拡張可能なデータモデルにします。

### 26-1. 構造と規則を分ける（確定2）

- 構造（データの形）：貢献の由来（改変元・基にした元）は、種まで全世代たどれる形で持つ。途中で切らない。世代の数をデータの形に入れない。
- 規則（Revenue Rule）：その Version に適用された Revenue Rule が、「由来のどこまでを報酬の対象にするか」「世代でどう重みを変えるか」を決める。Rule は版と適用開始日を持つので、後から範囲を変えても過去は遡らない（本編7章）。
- 例：A の曲 → B が編曲 → C が再編曲 → D がさらに派生（ケース61）。構造では D の Version から A まで必ずたどれる。A・B に報酬を届けるかは D の Version の Rule が決める。

### 26-2. 「同じ貢献は1回だけ」を2つに分ける（確定2の後段）

| | 何を決めるか | 誰が決めるか |
|---|---|---|
| 貢献の一意性（系譜の重複除去） | 1つの Version が同じ貢献を何度参照しても（直接と、由来を通しての両方でも）、その貢献は1つとして扱う。系譜の表示・「使われた作品」の数・チャンネルには1回だけ出す | 構造の決まり（固定） |
| 報酬の計算の基礎 | 同じ貢献・同じ人に、道ごとに数えて届けるか、1回にまとめるか | Revenue Rule（③で中身を決める） |

「貢献は一意だから報酬も必ず1回」とは固定しない。

## 27. ★★作品を構成する最小単位（1枚）

### 27-0. 3つの箱

- 貢献（Contribution）：人が作ったもの・演じたもの・仕上げたもの1つ。再利用条件は貢献に付く。
- 素材（Asset）：ファイル1つ（テキスト・譜面・MIDI・音声・動画・プロジェクトファイル）。★1つの素材は、1つ以上の貢献を「収めている」（例：伴奏の音声ファイルは、曲・編曲・演奏・録音を収めている）。
- Version：貢献の集まり（新しく作った貢献＋参照した既存の貢献）と、聴かせるための素材の組。

★素材を使うには、その素材が収めている全ての貢献の条件がそろう必要がある。素材そのものに別の条件は付けない（条件の持ち主は貢献）。
★役割（貢献の種類）は固定の一覧にしない。下の表は初期の行で、④では「種類の表に行を足せる」形にする（ラップ・ビート制作・コード進行・訳詞・プロデュース・映像・採譜・打ち込み などを後から足す）。種類の行ごとに「性質」（作品系・実演系・録音系・仕上げ）を持たせ、③の権利整理の手掛かりにする（判断ではない）。

### 29-3. 回帰で見つかった新しい破綻・注意点と、通し方の修正（確認用ケース 61〜65）

**ケース61　A の曲 → B が編曲 → C が再編曲 → D がさらに派生（えふさんの例）**
- 由来：編曲B（基にした元＝曲A）→ 編曲C（基にした元＝編曲B）→ Version D は C の伴奏素材（曲A・編曲C・演奏C・録音C を収める）を参照

- 報酬：D の Rule が「B（2代前の編曲）まで届けるか」「A に2本の道で数えるか」を決める
- 判定：○

**ケース62　★新破綻 N1：共作者が連絡不能・退会・死亡で、同意が永久にそろわない**
- 経過：詞AB（A・B の共作）。B が退会した。確定5「全権利者の必要な同意が揃わなければ使えない」により、詞AB は以後だれも使えない

- 通し方の修正：共作が生まれた時点（公開前の同意）で、共作者全員が「再利用の申請にどう返事するか」を前もって決めておける形を持つ。
  - 例：~~「A が代表して返事する」「どちらかの承認でよい」「全員の承認が要る」のどれかを、共作者全員が同意して選ぶ~~ → ★追補3 #3で修正：承認方式は「全員承認」か「代表者へ承認権限を委任（全員が事前に委任）」の2つを基本にする。「どちらか1人の承認でよい」は無条件の選択肢から外す（追補3 35章）

  - 前もって決めていない場合は、仕様どおり止まる（使えない）。退会・死亡の後の手続き（相続・代理）は③
  - ★追補3 #3：アカウント状態（退会・死亡・連絡不能）と権利状態は別の物。退会・死亡で権利は消えない。止まったものを後から1人の判断で解く形は持たない（追補3 35章）

## 32. ③への申し送り（TYP・Revenue Rule・権利・資金の流れ）

★追補3 40章で更新（Permission/Consent とアカウント状態・権利状態の分離、相続・退会・連絡不能、許諾の失効ルール、31-9）。

B系統（この文書）で決めた構造：由来は全世代たどれる／貢献は一意／使っていない貢献は報酬の候補に入らない／公開済み Version は書き換えない／同意と承認は消さない記録。以下は③で中身を決める。

### 32-1. Revenue Rule の計算

- 由来のどこまで（何世代）を報酬の対象にするか。世代で重みを変えるか（確定2）
- 同じ貢献・同じ人に複数の道で当たるとき、道ごとに数えるか1回にまとめるか（26-2）
- 組み合わせ（元が複数の家系）のとき、家系ごとの分け方（ケース13・14）
- 一部だけ使う・手直しした場合の重み（ケース15・52）
- 素材が収める複数の貢献（曲・編曲・演奏・録音）の間の分け方（27章）
- 定額・無償の参加（ケース25）
- 20/20/30/5/25 を初期テンプレートとして使うか・どの場面に当てるか（分配率は③）
- 全世代に届けたときの端数・少額の扱い（ケース45・60）

### 32-2. TYP

- Version 宛ての TYP を、その Version の Rule（TYP 種別）で由来まで届けるか（本編15-1）
- 「誰に何が届いたか」の内訳表示に必要な、分配1件ごとの記録（本編11章：出来事・Version・収益の種類・額・Rule の版・受取人ごとの額と経路。経路に「直接の参照か、何世代前の由来か」を足す）

### 32-3. 権利（法的な整理。★UI の再利用設定と同一視しない：追補1 17章）

- 原作品・共同著作・編曲（二次的著作物）・実演・録音物（原盤）それぞれの実際の権利関係
- 共作者の不在（退会・死亡・連絡不能）のときの手続き（ケース62・36・37）
- 公開時の派生許可を後から取り消せるか（本編15-15・ケース35）
- コード進行・鼻歌・AI 生成素材の扱い（ケース3・8・39）
- 外部で管理されている既存曲（ケース38）
- 音源分離などで持ち込まれた素材の扱い（ケース64）
- 未成年の参加（ケース40）

### 32-4. 資金の流れ

- 受け取りの保留（承認前・退会・本人確認前・盗用の申し立て中・共作者不在）と、保留の期限と行き先
- Stripe 等で受けた購入の収益が、Rule に沿って全世代の受取人へ届くまでの流れ（中央 API・中央 DB 側。utatane-backend は廃止方針：追補1 16-1）
- 視聴者5%（本編14章：第1実装に入れない。成立の条件）
